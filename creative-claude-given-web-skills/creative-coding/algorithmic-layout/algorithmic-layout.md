# Algorithmic Layout

**Skill ID:** `algorithmic-layout`  
**Layer:** 26 — Creative Coding  
**Goal:** Generate structured visual compositions from explicit constraints, data, and layout rules while preserving readability, responsiveness, semantic order, and predictable failure handling.

## Why This Matters

Algorithmic layouts break when randomness is mistaken for composition: titles collide with generated cards, long labels overflow their cells, mobile breakpoints retain desktop coordinates, and DOM order no longer matches visual order. Layouts built only from absolute positions also fail zoom and localization. The robust approach is to define constraints, generate a layout model, validate it, and render through CSS Grid/Flexbox or semantic DOM whenever possible.

## When to Use This Skill

Use this skill when building visual systems that are generated by rules, data, noise, character grids, or a p5.js sketch. Start with the simplest renderer that can satisfy the design. Treat the output as a production interface when it appears on a real page: content hierarchy, responsive behavior, accessibility, performance, and cleanup still matter.

## Core Concepts

### 1. Separate model from rendering

Represent layout decisions as data before applying them to DOM or canvas. This allows tests to inspect the layout without a browser screenshot.

**When to use:** Use when generating cards, editorial grids, dashboards, or variable portfolio compositions.

```js
const items = [{ id: 'a', span: 2 }, { id: 'b', span: 1 }];
function renderItem(item) { return `<article data-id="${item.id}" class="span-${item.span}"></article>`; }
```

**Gotcha:** Validate the edge case for this concept before adding more visual complexity. A result that looks correct at one viewport or one seed is not proof that the system is stable.

### 2. Constraints before coordinates

Specify minimum size, maximum columns, gutters, and reserved regions before assigning elements to cells.

**When to use:** Use when the same layout must work across different viewport sizes.

```js
const constraints = { minCardWidth: 220, gap: 20, maxColumns: 4 };
const columns = Math.max(1, Math.min(constraints.maxColumns, Math.floor((containerWidth + constraints.gap) / (constraints.minCardWidth + constraints.gap))));
```

**Gotcha:** Validate the edge case for this concept before adding more visual complexity. A result that looks correct at one viewport or one seed is not proof that the system is stable.

### 3. CSS Grid as the renderer

Let CSS Grid perform track sizing and reflow; use generated classes or CSS custom properties for intentional variation.

**When to use:** Use for most web page layouts instead of positioning every item with JavaScript.

```js
<section class="work-grid" aria-label="Selected projects">
  <article class="work-card">Project A</article>
  <article class="work-card">Project B</article>
</section>
<style>.work-grid { display: grid; grid-template-columns: repeat(auto-fit, minmax(min(100%, 16rem), 1fr)); gap: 1.25rem; }</style>
```

**Gotcha:** Validate the edge case for this concept before adding more visual complexity. A result that looks correct at one viewport or one seed is not proof that the system is stable.

### 4. Stable identity

Generated layout should use stable IDs, not array indices that change when data is sorted or filtered.

**When to use:** Use when interactive cards can be reordered or refreshed.

```js
const byId = new Map(items.map(item => [item.id, item]));
const selected = byId.get(selectedId);
```

**Gotcha:** Validate the edge case for this concept before adding more visual complexity. A result that looks correct at one viewport or one seed is not proof that the system is stable.

### 5. Responsive composition

Use layout rules that respond to available space rather than assuming one fixed canvas size.

**When to use:** Use for cards, dashboards, and editorial grids embedded in different containers.

```js
const layoutMode = containerWidth < 620 ? 'compact' : containerWidth < 980 ? 'medium' : 'wide';
```

**Gotcha:** Validate the edge case for this concept before adding more visual complexity. A result that looks correct at one viewport or one seed is not proof that the system is stable.

### 6. Text-aware sizing

Text length, language, and font metrics affect whether a layout remains valid. Do not compute fixed heights from sample copy alone.

**When to use:** Use for cards with user-generated content or multilingual titles.

```js
.card-title { overflow-wrap: anywhere; }
.card { min-width: 0; }
```

**Gotcha:** Validate the edge case for this concept before adding more visual complexity. A result that looks correct at one viewport or one seed is not proof that the system is stable.

### 7. Reading order and semantics

Visual variation must not reorder content in a way that contradicts the DOM reading order.

**When to use:** Use when using CSS order, grid placement, or algorithmic masonry.

```js
<main><section aria-labelledby="projects-title"><h1 id="projects-title">Projects</h1><article>First project</article><article>Second project</article></section></main>
```

### 8. Collision detection

For canvas or absolute-layout systems, detect overlap and define a fallback when constraints cannot be satisfied.

**When to use:** Use for generated posters, labels, diagrams, or node maps.

```js
function overlaps(a, b, gap = 0) { return a.x < b.x + b.w + gap && a.x + a.w + gap > b.x && a.y < b.y + b.h + gap && a.y + a.h + gap > b.y; }
```

### 9. Deterministic placement

A seed or stable ordering makes layout bugs reproducible and screenshots comparable.

**When to use:** Use when variation is desirable but QA needs repeatable results.

```js
const seedForItem = id => [...id].reduce((sum, char) => sum + char.charCodeAt(0), 0);
```

### 10. Progressive fallback

When a layout algorithm cannot place every item, fall back to a stable grid rather than dropping content.

**When to use:** Use for dense data, unknown content, and responsive transitions.

```js
const result = placeItems(items, constraints);
const safeLayout = result.complete ? result.layout : items.map((item, index) => ({ id: item.id, order: index }));
```

### 11. Resize observation

Recompute only when the container size changes, and avoid observer callbacks that mutate the observed dimensions endlessly.

**When to use:** Use for embedded layouts or visualizations whose container may change without a window resize.

```js

observer.observe(container);
// On teardown: observer.disconnect();
```

### 12. Visual regression testing

Test representative viewport widths and difficult content, not only the default desktop screenshot.

**When to use:** Use for generated dashboards and portfolio layouts where content can vary.

## Named Patterns

### Pattern 1: Constraint-based grid

**What it does:** Creates responsive tracks from minimum card width. Use for data-driven galleries.

**When to use:** for data-driven galleries.

```js
.grid { display: grid; grid-template-columns: repeat(auto-fit, minmax(min(100%, 15rem), 1fr)); gap: 1rem; }
```

### Pattern 2: Editorial feature span

**What it does:** Adds deliberate hierarchy while preserving a responsive grid. Use for a featured card among standard cards.

**When to use:** for a featured card among standard cards.

```js
.card--feature { grid-column: span 2; }
@media (max-width: 42rem) { .card--feature { grid-column: auto; } }
```

### Pattern 3: Collision-aware label placement

**What it does:** Avoids labels covering nodes or other labels. Use for diagrams and generated posters.

**When to use:** for diagrams and generated posters.

```js
const candidate = candidates.find(rect => placed.every(other => !overlaps(rect, other, 8)));
```

### Pattern 4: Data-first layout model

**What it does:** Separates content and layout decisions. Use when the layout needs unit tests or exports.

**When to use:** when the layout needs unit tests or exports.

```js
const layoutModel = items.map((item, index) => ({ id: item.id, group: item.category, priority: item.featured ? 0 : 1, index }));
```

### Pattern 5: Container-aware mode switch

**What it does:** Responds to the actual component width. Use for sidebars and embedded widgets.

**When to use:** for sidebars and embedded widgets.

```js
const observer = new ResizeObserver(([entry]) => setMode(entry.contentRect.width < 560 ? 'compact' : 'regular'));
```

### Pattern 6: Safe-grid fallback

**What it does:** Keeps all content visible if an advanced placement algorithm fails. Use for untrusted or highly variable data.

**When to use:** for untrusted or highly variable data.

```js
if (!isValidLayout(candidate)) return renderRegularGrid(items);
```

## Implementation Workflow

### 1. Define the visual contract

Write down the intended output, focal point, minimum and maximum density, palette, responsive behavior, and whether motion is essential. This prevents parameter tuning from becoming an endless visual guessing game.

### 2. Build a static baseline

Render one frame before adding animation. Confirm that the composition works without timing, input, or frame-rate variables. For a text-grid visual, validate monospace alignment first; for a p5.js sketch, confirm the host and canvas lifecycle.

### 3. Model before drawing

Create a data model for points, glyphs, particles, cells, or layout slots. Keep generation independent from rendering so you can inspect and test the model.

### 4. Add deterministic variation

Introduce a seed or stable input order. If the system is intentionally non-deterministic, provide a way to capture the seed and configuration that produced a problematic result.

### 5. Validate constraints

Check boundaries, overlap, valid numeric ranges, line lengths, minimum target sizes, and the reserved space around important text. Reject or repair invalid candidates rather than rendering them blindly.

### 6. Integrate controls

Make controls semantic and keyboard operable. Give labels meaningful names, expose current settings, and ensure a pointer-only interaction has a sensible keyboard equivalent.

### 7. Add motion deliberately

Choose the update rate and time model, cap delta time, and keep the static path available. Animate only the properties and objects that need movement.

### 8. Profile representative devices

Use DevTools Performance to inspect long tasks and frame time. Use the Network panel to check external libraries and assets. Test a small viewport and a lower-powered device rather than assuming a desktop is representative.

### 9. Test failure paths

Force invalid values, zero-sized containers, very long content, resize churn, missing assets, and reduced-motion settings. The fallback should preserve meaning even if the artwork is simplified.

### 10. Document reproducibility

Record parameters, seed, canvas dimensions, library version, and known limitations. This lets another developer reproduce the output without guessing.

## Debugging Checklist

- Confirm the container has a non-zero width and height before calculating coordinates.
- Log the effective element count after clamping, not only the requested count.
- Record seed, configuration, and viewport dimensions when reporting a visual bug.
- Use browser DevTools Performance recordings to identify long frames and repeated expensive work.
- Check the Network panel for failed fonts, scripts, and cross-origin image requests.
- Verify that resize observers and event listeners are disconnected on teardown.
- Test keyboard focus, focus-visible styles, screen-reader text, and reduced-motion behavior.
- Check Safari, Firefox, and Chromium where the feature relies on browser-specific APIs; confirm support before adopting newer syntax.

## Common Mistakes and Fixes

| Mistake | Why it fails | Fix |
|---|---|---|
| UNSEEDED | Random results change on every refresh and make bugs hard to reproduce. | Add a local seeded random generator and expose the seed in debug output. |
| UNBOUNDED | User-controlled density can create thousands of expensive elements. | Clamp the requested count and display the effective count in the UI. |
| DISTORTED | Resizing stretches the visual or changes its intended proportions. | Recompute from logical dimensions and preserve the design's aspect-ratio rule. |
| OVERDRAW | Large translucent layers are repainted every frame without need. | Reduce the number of layers and cache static elements to an offscreen canvas. |
| JITTER | Independent random values are used for smooth motion. | Sample a coherent field or interpolate targets over elapsed time. |
| WRAPPED | Character art wraps unexpectedly on narrow viewports. | Use preformatted whitespace inside a max-width scroll container. |
| LEAKED | Listeners, observers, or animation loops remain after unmount. | Return a teardown function that cancels frames and disconnects each observer. |
| INACCESSIBLE | The visual communicates information only through pixels or colour. | Add semantic labels, text summaries, and keyboard-accessible controls. |
| LOW_DPI | Canvas output appears blurry on high-density displays. | Scale the backing store by a capped devicePixelRatio and reset the transform. |
| OVERFLOW | Long labels escape their grid cells. | Allow wrapping for labels and set min-width: 0 on grid children. |
| MOTION | Continuous animation ignores reduced-motion preference. | Render one static frame and avoid starting the animation loop when reduced motion is active. |
| HOT_LOOP | Objects and arrays are allocated on every frame. | Reuse stable arrays and update existing objects in the render loop. |
| INVALID_INPUT | Malformed settings produce NaN coordinates or broken styles. | Parse, validate, clamp, and provide a safe default before regenerating. |
| NO_FALLBACK | A complex placement or renderer failure leaves a blank page. | Switch to a static image or conventional grid and log the failure context. |

## Mental Models

1. **A seed is a bug-report address.** It lets another person recreate the exact visual state.
2. **Constraints define the style envelope.** Variation should happen inside the chosen boundaries, not override them.
3. **Generation and rendering are separate jobs.** A data model can be validated even when the browser is not drawing.
4. **A static frame is a real product state.** Motion should enhance the result, not be required to understand it.
5. **The DOM is part of the composition.** Visual order, semantic order, focus order, and reading order must agree.
6. **Performance is a multiplication problem.** Sample count × work per sample × frame rate determines the cost.
7. **Fallbacks protect the message.** When a renderer fails, the user should still receive the content or a useful simpler view.
8. **Reproducibility makes art maintainable.** A visual system is easier to tune when its parameters can be repeated.

### Definition of done

- The visual matches its stated goal at desktop and mobile widths.
- Generated output is reproducible when a seed or configuration is supplied.
- No invalid setting can create an unbounded amount of work.
- Important text remains readable and does not overlap generated elements.
- Keyboard users can operate all controls and see a visible focus indicator.
- Reduced-motion users receive a usable static or paused presentation.
- Resource cleanup prevents duplicate canvases, listeners, or animation loops.
- A documented failure scenario falls back without blanking the experience.

## Production Notes

### Accessibility

Use semantic elements such as `main`, `section`, `figure`, `figcaption`, `button`, and `label` for the surrounding interface. A canvas is not a replacement for meaningful text. Decorative output can use `aria-hidden="true"` when an equivalent nearby description exists; meaningful visuals need an accessible name or a concise textual summary. Ensure all controls are reachable with the keyboard, show `:focus-visible`, and do not use colour as the only signal. Target WCAG 2.2 AA for the surrounding interface, including contrast and focus visibility.

```css
.visual-control:focus-visible {
  outline: 3px solid currentColor;
  outline-offset: 3px;
}

@media (prefers-reduced-motion: reduce) {
  .ambient-motion { animation: none; }
}
```

### Performance

Set a measurable budget before polishing. For interactive animation, aim for a frame time near or below 16.7 ms at 60 Hz, and investigate repeated frames above 20 ms. Cap device pixel ratio for large canvases, cache static layers, avoid unnecessary allocations in hot loops, and reduce sample count or octave count before increasing complexity. `will-change` is not a general performance switch; use it only after profiling. Avoid forcing layout reads and writes repeatedly in the same frame. If an effect is decorative, pause it when the document is hidden and when the user asks to pause it.

### Browser support

Test current Chromium, Firefox, and Safari. Feature-detect optional APIs such as `ResizeObserver`, and provide a window-resize fallback if container observation is unavailable. Check compatibility tables before depending on newer CSS or JavaScript APIs. A graceful fallback is preferable to a blank visual when a capability is missing. Avoid assuming that a browser's developer environment and production embedding environment have identical permissions, asset paths, or device pixel ratios.

### Security and data hygiene

Treat imported settings and user-provided text as untrusted. Validate numeric ranges, cap string lengths, and render text through `textContent` or escaped template interpolation. Never turn arbitrary user content into HTML merely to preserve visual formatting. If sharing configurations in URLs, validate decoded values and keep payload sizes bounded. Avoid placing private data in seeds, URLs, or exported metadata.

## Troubleshooting Recipes

### The artwork changes when unrelated code changes

Find every source of randomness and route it through the local seeded generator. Confirm that the same seed and configuration are used for both generation and export. Ensure iteration order is stable and that asynchronous asset loading does not alter the random sequence unexpectedly. Add a regression test that compares the generated model for a known seed.

### The output looks correct on desktop but breaks on mobile

Log the container's measured dimensions, logical drawing dimensions, and pixel ratio. Check whether the algorithm is using hard-coded coordinates or whether a long label is forcing a minimum width. Recompute from normalized coordinates or use responsive CSS tracks. Test at 320 px and at 200% zoom. If the composition cannot fit, use a deliberate scroll region or simplified layout rather than silently clipping content.

### The browser becomes slow after several minutes

Record a Performance profile and inspect whether frame callbacks multiply, arrays grow without bounds, or resources are recreated during every render. Check for duplicate listeners after rerenders. Disconnect observers and cancel animation frames during teardown. Reduce work per frame, cache static work, and stop animation when the page is hidden or reduced motion is active.

### The visual is invisible to assistive technology

Inspect the accessibility tree and the keyboard focus order. Confirm that the canvas has an appropriate nearby text alternative and that controls are real buttons with names. Decorative character art should not be announced character by character. Ensure keyboard users can pause, regenerate, or otherwise operate the same core functions without a pointer.

## References and API Accuracy

Use the official documentation for the selected runtime and verify version-specific APIs before shipping. For p5.js, distinguish global mode from instance mode and use the documented lifecycle methods. For Canvas 2D, verify `getContext`, `requestAnimationFrame`, `ResizeObserver`, and cleanup behavior against current browser documentation. Check browser support for CSS features such as `:focus-visible` and `prefers-reduced-motion`. Do not rely on an editor-only environment as evidence that production embedding is correct.
